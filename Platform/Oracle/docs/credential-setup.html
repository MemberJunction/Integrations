Connection setup

Connect your Oracle database

Give us a read-only login and a few connection details, and we'll sync data straight from your Oracle database. About ten minutes, with help from whoever manages the database.

Read-only 5 values to send ~10 minutes

Before you start

You'll need someone with Oracle DBA access — a user (such as SYSTEM) able to run CREATE USER and GRANT. When you're done you'll have five values to send us: the database host, port, and service name, plus the username and password of a dedicated read-only account you'll create below.

  1. 1

    Gather your connection details

    From your DBA or your tnsnames.ora file, collect these three:

    • Host — the database server's hostname or IP address (e.g. db.internal.example.org or 10.0.4.12).
    • Port — the Oracle listener port. The default is 1521; only change it if your DBA uses a non-standard port.
    • Service Name — the database service to connect to (e.g. ORCLPDB1, FREEPDB1). If your DBA gives you a SID instead of a service name, that's fine too — just tell us which one it is so we connect correctly.

    Together these form Oracle's Easy Connect string, host:port/service_name. If your DBA would rather hand us a full Oracle connect string or TNS descriptor (for a SID, a load-balanced address list, or custom options), we accept that in place of the three fields above.

  2. 2

    Create a read-only user

    Please give us our own login rather than sharing an existing account — it keeps our access separate and easy to revoke. Run the following as a DBA (for example SYSTEM), choosing a strong password and adjusting the grants to cover the data we should read:

    -- Run as a DBA (e.g. SYSTEM). Replace the password with a strong secret.
CREATE USER mj_readonly IDENTIFIED BY "ChooseAStrongPassword";

-- Allow the user to log in
GRANT CREATE SESSION TO mj_readonly;

-- Broadest option: let the user read every table in the database
GRANT SELECT ANY TABLE TO mj_readonly;

-- ...OR, more tightly scoped: grant SELECT on only the tables we need
GRANT SELECT ON hr.employees   TO mj_readonly;
GRANT SELECT ON hr.departments TO mj_readonly;

    Which grant? SELECT ANY TABLE is the simplest — one line, and we can read anything. Per-table GRANT SELECT ON … statements are more work but limit us to exactly the tables you choose. Either is fine; pick whichever fits your policy.

    On a multitenant (PDB) database, create this user inside the pluggable database we'll connect to — not in the CDB root. (A common user in the root would need a C## prefix and is usually not what you want here.)

  3. 3

    Make sure the database is reachable

    The Oracle listener must be reachable from MemberJunction's network on the port from Step 1:

    • Open your firewall / security group so our servers can reach the database on that port (default 1521). We'll send you the IP addresses to allow.
    • Confirm the listener is running and serving your database — on the DB host, lsnrctl status should list your service.
    • If the database sits behind a VPN or private network, let us know — we'll arrange the right connectivity.

  4. 4

    Encrypted connections (TLS / TCPS) — optional

    If your database requires or offers encrypted connections, we support Oracle's native TLS (TCPS). Just tell us and we'll enable it on our side. TCPS usually listens on a separate port (commonly 2484), so send us that port instead of 1521, along with the same service name. If you don't use TLS, you can skip this step.

You're done

Send us these values

db.internal.example.org Oracle
1521 Oracle
ORCLPDB1 Oracle
mj_readonly Oracle
•••••••••••••••• Sensitive

Treat the login like a password. Share the username and especially the password only with us, over a secure channel — not plain email or chat if you can avoid it. The account above has SELECT only, so it can read your data but can never change or delete it. You can revoke our access completely at any time by running DROP USER mj_readonly CASCADE; on the database.
