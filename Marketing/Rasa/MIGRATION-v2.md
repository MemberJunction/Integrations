# rasa.io connector — v1.x → v2.0.0 migration record

This is a **breaking (major)** release. It is a `redo`: the connector was re-extracted from the vendor's
own API sources and its metadata catalog was rebuilt from scratch. The prior 8 objects were **renamed, not
removed** — every one maps 1:1 onto a v2 object, so there is **no capability loss**. The break is the
identity change (object and integration names), which any deployment referencing the old names must absorb.

## 1. The Integration row is RENAMED, not replaced

| | v1.x | v2.0.0 |
|---|---|---|
| `Integration.Name` | `Rasa.io` | `rasa` |
| `Integration.ClassName` | `@memberjunction/connector-rasa-io` | **unchanged** |
| `Integration.ImportPath` | `@memberjunction/connector-rasa-io` | **unchanged** |
| `Integration.ID` | `1DD0F81E-A3CC-4236-89B5-FB6F0EBDAA50` | **unchanged** |

The row ID is deliberately preserved so existing `CompanyIntegration` rows, stored credentials and sync
history keep pointing at the same integration. The v2 seed migration therefore **UPDATEs** this row; it does
not insert a second one. A migration that inserted instead would orphan every v1 deployment's
`CompanyIntegration` and its credential.

**`ClassName` is deliberately NOT changed.** This repo's catalog convention is `ClassName` == the npm package
name, so instance discovery matches; v1.1.0 already migrated to it (see
`.changeset/connector-rasa-io-classname-package-convention.md`, which rolled the change out to existing
tenants via a delta migration). Changing it to the short `RasaConnector` key would regress that convention
and break instance discovery. The class registers **both** keys — the package name as canonical, and
`RasaConnector` for continuity with any tenant row still carrying the short name — so either value resolves.
The rename in this release is therefore `Integration.Name` only.

## 2. All 8 v1 objects map 1:1 (rename only — no capability removed)

| v1 object name | v2 object name |
|---|---|
| `persons` | `Person` |
| `posts` | `Post` |
| `insights-actions` | `Insight Action` |
| `insights-topics` | `Insight Topic` |
| `person-attributes` | `Person Attribute` |
| `analytics-activities` | `Analytics Activity` |
| `analytics-articles` | `Analytics Article` |
| `analytics-topics` | `Analytics Topic` |

v1 used the vendor's URL slugs as object names; v2 uses MJ's singular PascalCase convention, which is what
determines the destination table name. **Consequence: destination tables are renamed.** A deployment that
already synced v1 data will, after upgrading, sync into new tables (`rasa.Person`, not `rasa.persons`) and
the old tables are left in place, untouched. Re-point any downstream views/reports at the new names, then
drop the old tables when you're satisfied. Nothing is dropped automatically — that would destroy client
data on a version bump.

The 8 prior `IntegrationObject` rows (and their `IntegrationObjectField` children) are deleted by
`V202608011400__rasa-io__Deprecate_v1_Objects`, which runs immediately after the v2 seed. It is a separate
migration rather than part of the seed because the seed is generated by `mj sync push`, which is
upsert-with-no-prune and therefore emits only the new rows. Without the delete the v1 objects would remain
`Active` and sync the same vendor endpoints a second time into the old slug-named tables. The delete is by
hardcoded ID, so it is a no-op on a database that never had v1. Destination tables are not dropped.

## 3. v2 adds 26 objects (34 total)

Beyond the 8 renames, v2 declares 26 additional objects spanning the person-child surface
(`Person Action` / `Person Topic` / `Person Send`), newsletter content (`Newsletter`, `Section`, `Blast`,
`Content Pool Item`, `Lead Post`), the subscription/sequence surface, contacts, deletion feeds
(`Deleted Person`, `Deleted Contact`) and the v2 messaging/list objects.

**16 of the v2 objects are `auth-gated-exists` only** — HTTP 401 proves the path is real and auth-gated, but
the credential available during the build lacked v2 scope, so their payload shape is unverified against live
data. They remain declared: credential scope is a *testing* limitation and must never shape the catalog. See
`SuperCoordinatorReport.md` for the per-object evidence tier.

## 4. The 12 Actions were RETARGETED (required — they would otherwise all fail)

Each Action's `Config` carries the routing pair `IntegrationName` + `ObjectName`, which
`IntegrationActionExecutor` resolves at run time (`LoadIntegrationEntity` does an exact
`Name='<IntegrationName>'` match). Both values were stale after the rename, so **all 12 Actions were updated**:

- `Config.IntegrationName`: `Rasa.io` → `rasa` (otherwise every Action throws `Integration "Rasa.io" not found`)
- `Config.ObjectName`: the 4 slugs → their v2 names (`persons`→`Person`, `posts`→`Post`,
  `insights-actions`→`Insight Action`, `insights-topics`→`Insight Topic`)

Action **names** (`Rasa.io - Get Person`) and the `Rasa.io` Action Category are human-facing labels and are
intentionally left unchanged — the vendor's brand is still rasa.io; only the MJ integration row's name is
lowercase `rasa`. Renaming them would add a category-rename dependency to the migration for no functional gain.

## 5. Carried forward from v1 (do not drop)

`BatchMaxRequestCount=50`, `BatchRequestWaitTime=200` and `Icon='fa-solid fa-newspaper'` are carried forward
from v1.1.0. They are nullable in the metadata slot table, so their absence would not have failed a floor
gate — but dropping them would silently regress request throttling and the MJCentral icon for every existing
deployment. Carried as prior-version continuity, not re-derived from live data.

The credential type (`rasa.io API`, ID `B7A2E41C-93D5-4F8E-A610-5D3C8F2B9E07`) is **unchanged** — same four
fields, same required set. Only its `Description` was expanded to record the non-obvious auth detail: the
JWT obtained from `POST /v1/tokens` is presented as a **`rasa-token` request header**, not as
`Authorization: Bearer`.

## 6. Upgrade checklist

1. Apply the v2 seed migration (SQL Server and/or PostgreSQL twin).
2. Confirm `Integration.Name` is now `rasa` and 34 objects are present.
3. Re-run setup for the integration so the 34 destination tables materialize. `Content Pool Item` has no
   documented field schema (the vendor's Swagger references `ContentPoolApiGetResponse` but never defines
   it), so its columns come from the first live sample via runtime sample-union — if that first page is
   empty the object materializes with no columns; re-run once data exists.
4. Re-point downstream consumers from the old slug-named tables to the new PascalCase tables, then drop the
   old tables at your discretion.
5. Verify the 12 Actions execute (they resolve by the updated `Config` routing pair).
